# 协议实现证据

来源：用户提供的 `XTW-5.exe`，SHA-256 `fe9768d278ce56a4dcd04689b86390b9ae43889956bf4788f0ef7283ad2d1faf`。
原始反编译工程与厂家二进制保留在本地分析目录，不随本仓库分发。

## 传输和帧

`1a86:1001`，接口 0，Bulk OUT 02 / IN 81。厂家教程截图明确把接口 0 绑定为 WinUSB。

```text
02 CMD 00 01 LEN_BE16 PAYLOAD CRC_BE16
```

CRC 初值 FFFF、反射多项式 A001、不做 final xor，覆盖 CMD 至 payload，CRC 高字节先传。`004417a4` 和 `004417ec` 已核对汇编及二进制表。
例：设备信息请求 `02 10 00 01 00 00 03 b4`。

普通交换函数 `0044c58c` 写完调用 `0043a9f0(1000)`，其计时比例为 100000，实际为 **10 ms**，随后最多读 512 字节。WinUSB 超时 2000 ms。
读取芯片时 `34` 响应是原始数据流，不能经过普通命令响应解码器。

2026-10-06 实机确认：XTW5F-1.1.5.R1 的设备信息命令 10–13 回显原命令，头部为 `02 CMD 00 01 LEN_BE16`，尾部为两个零字节，**不是请求格式的 CRC**。仅这些信息命令允许该零尾部，仍检查长度和命令；不能检测有效载荷中无校验保护的位错误。原始抓包保留于本地，回归测试使用同格式报文（设备序列字段已替换为占位值）。

芯片识别 31 经厂家 `00441bf8` 确认使用相同接收辅助函数且精确要求 6 字节载荷。2026-10-06 实机已抓到识别响应 `02 31 00 01 00 06 25 c8 40 17 00 ff 00 00`，确认 6 字节载荷和零尾部。配置 39、流程控制 20 的响应则为下述通用空应答；擦除 32 与写入 35 的实机应答见下文。

厂家识别按钮调用 `00441bf8` 在 `00446928` 配置命令之前，因此 GUI 自动识别直接发送无参数 31，不依赖型号、地址、长度或 SPI 速率。命令没有插座参数，仅为主插座提供入口。`00414044` 只判断高字节 24；非 24 路径在 `00414685` 执行 `AND 00FFFFFF`，再调用 `0043FC2C` 按低 24 位匹配原厂库和用户库，**没有要求高字节为 25**。之前 Linux 的 25 限制是错误假设，已删除。高字节 24 时只列出类型 2 的候选，因厂家库中 EEPROM ID 为 0，不能借此确定容量。多候选默认按厂家 AutoDetect=1 的行为选中库中第一项；关闭该选项则清除选中项、等待手选。详细静态分析见 [windows-detection.md](windows-detection.md)。

voltageCode：1800mV → 1，5000mV → 2，3300mV → 0。拒绝其他电压，而不照搬原厂的默认落入 0。
实机写入 35 返回 `02 35 00 01 00 01 00 00 00`：一字节状态 00、零尾部。00 代表本次请求的正常应答，不作为最终数据正确的证明；写后仍须全量回读校验。未知非空状态被拒绝，兼容通用空 ACK，但未在当前芯片上观察到该写入 ACK 变体。
EEPROM 清空通过全片写 FF，原厂也走填充写入路径，不发送 NOR 擦除命令。

## 厂家数据库

`0043a070` 按 8 字节调用 `00439520`，为 3DES EDE / ECB 解密。24 字节密钥由用户提供的已校验 EXE 在 VA `007dd034` 处读取；无需运行 EXE。
解码后有 96 字节头，魔数 `55 AA AA 55`，偏移 4 为 LE32 条目数；随后每条 96 字节。文件尾可能有额外数据，条目数以头为准。

| 记录偏移 | 内容 |
| --- | --- |
| 0、16 | 型号、厂商，最大 16 字节，到首个 NUL 截断；不能把 NUL 后的旧缓冲区字节当文本 |
| 32 | LE32 容量（字节） |
| 36 | LE32 块 / 扇区大小 |
| 48 | LE32 JEDEC ID |
| 52 | LE16 电压（mV） |
| 54 | LE16 页大小 |
| 56 | 协议类型 |
| 57、58 | 厂家配置 flags，原样保留 |
| 60 | LE32 擦除等待时间参数 |

20250524 库：920 个类型 1、243 个类型 2、9 个类型 4、1 个类型 8，共 1173 条。部分 JEDEC ID 重复是正常现象，GUI 保留候选而不猜测实际型号。

模拟器用于验证请求构造、UI 状态和缓冲区流程，它复现的是本次静态分析得到的协议模型，不能作为硬件协议正确性的独立证明。

## 实机读取与通用空应答

配置 39、流程控制 20（开始 1、结束 0）实机均返回 `02 00 00 01 00 00 00 00`。它不回显请求命令号，尾部也不是请求格式的 CRC。厂家 00446928 仅检查 USB 交换成功，0044191c 仅通过 00441830 检查非空与帧头。39 和 20 接受这条精确的 8 字节应答；35 兼容此格式，但当前实机观察到的是带状态 00 的 35 回显。识别、速率、擦除不接受通用空应答。

使用主插座、默认 SPI 速率、GD25Q64C 参数（3.3 V，8 MiB）两次整片读取成功，文件逐字节一致。读取发送 34 命令，每次取 4096 字节原始数据，末块地址 007FF000。没有执行写入或擦除。详见 hardware-validation.md。

## 写入与校验补充核对

- 32 擦除命令的准备 FF、启动 00 阶段均返回一字节 00；轮询 01 在忙时返回 00，完成后为 55。原先将准备 / 启动也要求 55 是错误的。保留超时与擦后全片查空。
- 35 使用 1024 字节内的整页分块；自定义页大小不是 1024 的因数时向下取整到整页倍数，避免跨块页未对齐。
- 读取调用方 004240DC 向 0043AA9C 传入 1，该函数计时比例为 1000000，含义是至少 1 微秒等待。本实现已补上该延时。
- 一次测试写后立即回读在 0000046E 报差异；独立重读 8 MiB 后与测试文件完全相同。尚未确定低层瞬态原因，不将其描述为已定位的物理故障。实机校验遇到数据不符时记录首个差异，重新配置并完整重读最多一次；第二次仍不符则报错，不重写芯片、不跳过比较。模拟器保持单次读取以便确定性注入错误。
