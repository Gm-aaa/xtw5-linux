# Windows 检测流程核对

对象：用户提供的 20250524 版 XTW-5.exe。以下证据来自 Ghidra 反编译及 x86 汇编交叉核对，不是实机抓包。

1. 检测按钮处理函数 `00413E48` 在 `0041401B` 调用 `00441BF8`，没有先发送芯片配置。
2. `00441BF8` 构造无参数命令 31，经 `004417EC` 添加请求 CRC，再调用 `0044C58C` 交换数据。
3. 接收辅助函数 `00441830` 只检查收到的数据非空、首字节为 02；检测函数另外要求载荷长度恰好为 6。厂家这里没有校验响应 CRC。
4. `00441C74–00441CA2` 将载荷前 4 字节按大端顺序拼成 32 位值，后 2 字节分别写入独立输出参数。ID 匹配函数没有使用后两字节。
5. 调用方 `00414038–0041404A` 只特殊处理 `(value & FF000000) == 24000000`；这条分支进入 24 系列选择流程。
6. 其他返回值在 `0041467F–0041468C` 明确执行 `value & 00FFFFFF` 后传入 `0043FC2C`。
7. `0043FC2C` 遍历原厂库和用户库的 76 字节内存记录，比较记录偏移 18（十六进制）的完整数据库 ID 与上一步的低 24 位值，保存首个匹配项并统计匹配数量。
8. 没有匹配会提示；多匹配时 `00414BE7–00414C02` 在一个全局选项关闭的情况下打开候选选择窗口（`004403C4`）。配置读取代码确认该全局选项为 `[PrjInfo] AutoDetect`，GetPrivateProfileIntA 默认值为 1。开启时跳过候选窗口，使用首个匹配项。Linux 已改为相同默认行为，设置中可关闭。

关键修正：旧 Linux 代码错误地要求 SPI 返回值高字节必须为 25。举例，合成响应载荷 `00 EF 40 18 00 00` 在 Windows 路径中按 EF4018 匹配，旧 Linux 会拒绝。现在对非 24 返回值统一按低 24 位匹配，保留原始 32 位值和附加字节到日志。全零、全 FF 的无效 SPI ID 仍不当作识别成功。

验证：核心测试覆盖高字节 00、01、25、FF，及 24 特殊路径、错误长度、无效 ID 和重复型号；GUI 热插拔测试及模拟器改用高字节 00，避免测试只重复原先的错误假设。

限制：以上证实了代码中的匹配差异；尚未取得用户当前芯片的实际 31 响应，不能据此宣称该芯片已在 Linux 识别成功。实机 CRC 尾部和附加字节语义仍需实际报文验证。

## 当前芯片的界面证据

2026-10-06 从正在运行的 GUI 确认返回 ID 为 `25C84017`、匹配 6 项。原厂库依次为 GD25Q64C、GD25B64C、GD25Q64、GD25Q64B、GD25Q64E、GD25B64E，均为 GIGADEVICE、8 MiB、3.3 V、256 字节页，flags/flags2 均为 0。Windows 默认规则会采用第一项 GD25Q64C；这属于默认匹配策略，并不证明读取了能区分具体后缀的额外身份信息。Linux 之前强制手选正是此次表现差异。
